# Snapshot provenance and reproduction boundaries

Source hashes identify the implementation that generated a historical snapshot. They are not a promise that the current working tree, its CLI or every later editorial sentence has the same bytes. Historical identities are retained; later reproduction records are appended separately.

## Effectiveness integration and numerical verification

The [integration manifest](../reports/effectiveness_snapshot/integration_manifest.json) retains the original 2026-10-04 bundle hashes and maps six original scripts to their portable versions. Publication in `dd1c4a9` initially checked syntax, CLI behavior and identities; it did not rerun the full financial calculation. The [2026-10-05 reproduction record](../reports/reproduction_check/README.md) now closes that numerical gap: 25 public CSV tables and three core JSON summaries agree with regenerated outputs, with maximum absolute numeric difference zero.

The JSON comparison excludes only explicitly listed top-level raw/script provenance fields, whose locations or identities changed during portability. Numerical observations, coefficients, intervals, calibration settings, labels and all other fields are compared. Input and portable-script identities are recorded separately in the [verification manifest](../reports/reproduction_check/verification_manifest.json). The main engine also rebuilt the baseline from saved price/risk-free inputs; the mechanism comparison uses that fresh baseline and records all six derived inputs, including both daily dollar-P&L files. The rerun's independent audit is also retained; numerical agreement alone is not an independent implementation check.

**Figure rendering remains outside this verification.** The two effectiveness PNG files were created by the old one-machine report builder, which is not included in the portable numerical pipeline. They remain historical artifacts; this rerun did not redraw them or verify their rendering. The underlying numerical tables were reproduced. The French memo's portable summary writer was not run in the numerical check either, so the check does not certify narrative regeneration.

## Random-control storage and risk follow-up

The first public random-control protocol and results appeared together in `dd1c4a9`; the author records writing the methods before running them, but this is not independently timestamped public preregistration. The [updated protocol](../research/random_control_protocol_zh.md) makes this distinction explicit.

The same saved prices, 4,096 draws per method, seeds and 0/5/10 bp scenarios were rerun to produce gzip-compressed CSVs and add maximum-drawdown percentiles and peak/trough dates. These risk diagnostics were added after viewing the first results. All pre-existing summary values, selection hashes and the small distribution/ledger tables are unchanged. Every compressed CSV decompresses to the exact bytes of its prior public CSV. The [storage manifest](../reports/random_control_snapshot/storage_manifest.json) records this check and the prior commit, while [summary_dd1c4a9.json](../reports/random_control_snapshot/summary_dd1c4a9.json) retains the original producer/protocol hashes. The new [summary](../reports/random_control_snapshot/summary.json) records the actual rerun's source hashes and time.

Compression reduces the ten CSVs in the current checkout from 3,604,535 to 1,529,527 bytes; all paths and cost levels remain available. Previous plain CSVs remain in Git history, so this does not claim that the full repository's clone history has shrunk.

All records concern retrospective revised historical data. They establish calculation traceability and reproduction on the saved inputs, not supplier-data accuracy, publicly preregistered hypotheses, prospective validation or investment performance in a live account.
